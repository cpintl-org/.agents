Architecture of an Autonomous NGO
Operations System Within the Google
Workspace Ecosystem
Architectural Foundations and Operational Model
Operating an enterprise-grade Non-Governmental Organization (NGO) software ecosystem
without external cloud infrastructure—such as standalone Google Cloud Platform (GCP)
projects, Amazon Web Services, or Microsoft Azure—requires rearchitecting Google Workspace
into an integrated platform-as-a-service (PaaS) and database-as-a-service (DBaaS). In this
serverless topology, Google Drive operates as a globally distributed object storage layer, Google
Sheets serves as an indexed relational datastore, and Google Apps Script (GAS) provides an
event-driven serverless compute runtime.
Traditional cloud components are mapped directly to native Workspace primitives. Relational
tables become structured worksheets, cron schedulers become Apps Script time-driven triggers,
compute containers become V8 script instances, and web gateways become managed Web
App deployments. The browser presentation tier is delivered through Google Sites hosting
single-page applications (SPAs) embedded via Apps Script HTML services. System
integrations, field dispatching, automated stakeholder messaging, and intelligence pipelines
execute through native Workspace APIs and Google AI Studio endpoints.
This design eliminates recurring infrastructure costs, operational software licensing, and
administrative overhead beyond standard Google Workspace licenses. Achieving
enterprise-grade reliability, however, requires working within the architectural boundaries of
Google Workspace. System designs must account for strict quota limits, non-configurable
execution timeouts, unique cross-origin resource sharing (CORS) behaviors, and specialized
iframe sandboxing models.

File System and Storage Tier: Drive Internals and
Content Delivery
Google Drive functions as an object store that references files through unique, immutable
alphanumeric strings rather than traditional hierarchical POSIX file paths. Within the Apps Script
runtime, files are encapsulated inside binary Blob objects. When data is ingested—such as
identity documents, grant applications, donation receipts, or medical logs—Drive automatically
calculates checksums, detects MIME types, and indexes metadata. File types that lack an
explicit Content-Type header are designated as application/octet-stream. Conversely, structured
JSON models, vector assets, and web media preserve their declared MIME signatures
throughout their storage lifecycle.
Drive does not support in-place byte-level mutation. Mutating an existing record requires
streaming a complete replacement blob or creating an explicit new file revision. For high-volume
file pipelines, systems must use chunked multipart uploads or append-by-versioning strategies
to avoid memory exhaustion in both client and server runtimes.
Historically, static web hosting on Google Drive relied on direct public web delivery endpoints.
When Google deprecated native folder hosting, developers shifted to the
https://drive.google.com/uc?export=view&id={file_id} redirection pattern. However, modern
browser privacy policies and the widespread phase-out of third-party cookies have
compromised this delivery path.
When assets are accessed through the legacy uc endpoint, Google's reverse proxy evaluates
user session cookies. When a browser blocks third-party cookie transmission, the storage
gateway fails to authenticate access, returning broken image displays, continuous redirect
loops, or HTTP 403 Forbidden errors.
To deliver web-ready static assets—including user interface scripts, cascading stylesheets,
vector icons, and static assets—into external client browsers or embedded frames, architectures
must use Google's distributed user-content edge nodes:

When assets are stored in a Shared Drive with permissions set to "Anyone with the link can
view", client applications can extract the corresponding file ID and map it directly to
lh3.googleusercontent.com/d/{file_id}. This routes delivery through Google's distributed cache,
ensuring low latency in production web environments.
Cross-origin interactions introduce distinct constraints. Requests sent directly to
drive.google.com do not include permissive Access-Control-Allow-Origin headers and enforce
X-Frame-Options: SAMEORIGIN policies. As a result, direct client-side XMLHttpRequests or
fetch invocations against raw Drive URLs fail.
Drive also strips HTTP Range headers (Accept-Ranges: bytes) across its public distribution
endpoints, which prevents media seeking and dynamic binary streaming.
Consequently, client applications cannot fetch structured configuration files, raw CSV datasets,
or spatial vectors directly from raw Drive endpoints. Instead, access must be brokered through
an Apps Script Web App acting as a CORS proxy gateway, or loaded directly in memory by
client runtimes executing within the same domain scope.

Database and Persistence Architecture
Operating an NGO system requires strong data persistence across constituent management,
donation accounting, grant records, field dispatching, and inventory. Without an external SQL
engine, the Workspace environment utilizes a multi-tiered data storage pattern.
Google Sheets functions as the core transactional engine. Workbooks operate as discrete
schemas, while individual worksheets serve as indexed tables. Entities are structured with
explicit field types across defined columns, using the first row as a schema declaration and
subsequent rows as record entries.
Because multiple web apps, intake forms, and automated routines can write to the same
spreadsheet simultaneously, the architecture must prevent race conditions, dirty reads, and
record overwriting. To maintain atomicity, all mutation operations must run inside the Apps Script
LockService. Without locking, concurrent execution threads can interleave spreadsheet row
evaluations, leading to data loss and corrupted row structures.
The LockService API exposes three mutual exclusion scopes:
   ●​ Script Locks: LockService.getScriptLock() establishes a global critical section across all
       users and executions invoking that specific Apps Script deployment. This is required for
       serializing operations across shared database tables.
   ●​ Document Locks: LockService.getDocumentLock() isolates execution to a single
       container file, such as a bound spreadsheet. This is used when modular scripts share
       access to an underlying sheet document.
   ●​ User Locks: LockService.getUserLock() restricts isolation to the active user account. This
       is used to prevent duplicate user submissions while allowing background pipelines to
       proceed concurrently.
Because Google Sheets does not provide native transaction logs or isolation configurations, the
architecture implements Software Transactional Logging. Before applying batch
operations—such as debiting an inventory balance while logging an aid allocation—the script
serializes the target rows into a temporary snapshot within CacheService. If an unhandled
exception occurs before SpreadsheetApp.flush() runs, the catch block restores the previous row
state, maintaining atomicity and consistency.
/**​
 * Executes an atomic transaction against the operational sheet.​
 * @param {string} sheetName Name of the table worksheet.​
 * @param {Function} mutationCallback Atomic write operation callback.​
 * @returns {any} Result of the mutation callback.​
 */​
function executeAtomicTransaction(sheetName, mutationCallback) {​
   const lock = LockService.getScriptLock();​
   // Wait up to 30000ms (30s) to acquire the critical section mutex​
   const hasLock = lock.tryLock(30000);​
   ​
   if (!hasLock) {​
      throw new Error("System concurrency error: Database transaction
timed out waiting for lock.");​
   }​
​
    try {​
       const spreadsheet = SpreadsheetApp.getActiveSpreadsheet();​
       const sheet = spreadsheet.getSheetByName(sheetName);​
       const result = mutationCallback(sheet);​
       // Flush all pending row calculations and operations to disk​
       SpreadsheetApp.flush();​
       return result;​
    } finally {​
       lock.releaseLock();​
    }​
}​

Google Sheets enforces a hard limit of 10 million cells per workbook. Sequential row scans
using Range.getValues() can introduce high latency due to serialization overhead between the
V8 execution environment and the spreadsheet engine. To keep query response times under
one second, the system uses three indexing approaches:
  ●​ In-Memory Array Processing: The system avoids individual cell reads. It loads entire
      datasets into memory in a single call using sheet.getDataRange().getValues(), filters
      arrays natively within V8, and commits updates in batches with Range.setValues().
  ●​ Fast Primary Key Scanning: To retrieve a record by its identifier without reading entire
      sheets into memory, the system uses the spreadsheet engine's underlying search
      indexing via createTextFinder():​
      function findRowById(sheet, id) {​

  ●​ Volatile Caching: Reference data that changes infrequently—such as chart-of-account
      identifiers, program codes, and volunteer skill registries—is serialized into CacheService
      with a 6-hour time-to-live (TTL). Read queries check the cache first, avoiding round trips
      to the spreadsheet engine.
For high-volume, read-heavy workloads (such as spatial coordinates for field routing or archival
case management), Sheets can be augmented or bypassed:
  ●​ Newline-Delimited JSON (NDJSON) on Drive: Archival records and grant documents
      are written as NDJSON files directly to dedicated Google Drive folders. The file IDs are
      stored in an index sheet. Apps Script parses these blobs using stream buffers, avoiding
      Sheets cell limits.
  ●​ Client-Side WASM SQLite (sql.js): The web client downloads an encrypted binary .sqlite
      database file stored in Google Drive. Using WebAssembly, the client instantiates SQLite
      entirely in browser memory. Queries run instantly on the client side with full ANSI SQL
      support. When updates occur, the updated SQLite binary is transmitted to the Apps Script
      backend, locked, and overwritten in Drive, providing an offline-first data model for remote
      field workers.

Serverless Backend Infrastructure: Apps Script
Execution Engine
Google Apps Script runs on Google's V8 runtime, supporting modern ECMAScript standards
such as arrow functions, const/let, asynchronous functions, and destructuring. Unlike
long-running server environments or containerized microservices, Apps Script operates under
serverless execution constraints:
   ●​ Execution Timeouts: Script invocations face a strict 6-minute execution limit on Google
       Workspace Business and Enterprise accounts.
   ●​ Concurrency Ceilings: A single user account can run a maximum of 30 simultaneous
       script executions.
   ●​ Daily Compute Quotas: Scripts are constrained to 6 hours of aggregate execution time
       per day on Workspace accounts.
To run long-running batch operations—such as generating thousands of PDF tax receipts or
processing bulk geocoding jobs—without hitting the 6-minute timeout, the system uses
self-replicating triggers.
The script tracks its own execution time using new Date().getTime(). When execution reaches
4.5 minutes, the script saves its state, sets an installable time-driven trigger to resume
processing one minute later, and exits cleanly:
function runLongRunningBatchMigration() {​
   const START_TIME = new Date().getTime();​
   const MAX_RUNTIME_MS = 270000; // 4.5 minutes execution threshold​
   const properties = PropertiesService.getScriptProperties();​
   let cursor = parseInt(properties.getProperty("MIGRATION_CURSOR") ||
"0", 10);​
   ​
   const dataset = getDatasetRows(); // Retrieves large array​
   ​
   while (cursor < dataset.length) {​
      if (new Date().getTime() - START_TIME > MAX_RUNTIME_MS) {​
         properties.setProperty("MIGRATION_CURSOR", cursor.toString());​
         ScriptApp.newTrigger("runLongRunningBatchMigration")​
                       .timeBased()​
                       .after(60000)​
                       .create();​
         return;​
      }​
      ​
      // Process unit of work​
      processRecord(dataset[cursor]);​
      cursor++;​
   }​
   ​
   // Cleanup once batch completes​
   properties.deleteProperty("MIGRATION_CURSOR");​
   deleteTriggersByName("runLongRunningBatchMigration");​
}​

Google Apps Script projects deployed as Web Apps expose two HTTP entry points: doGet(e)
and doPost(e). Production deployments require two configuration choices:
  ●​ Execute as: Setting this to Me (your account) executes all operations using the
     developer's permissions, allowing the script to read and update underlying data stores
       without exposing raw access directly to users.
   ●​ Who has access: Configured as Anyone within domain for internal operational portals, or
       Anyone for public donor portals and webhook endpoints.
Consuming an Apps Script Web App from an external single-page application or client-side
interface introduces an architectural challenge: the HTTP 302 redirection flow. When a client
sends a request to https://script.google.com/macros/s/{id}/exec, Google does not return the
payload directly. Instead, it issues an HTTP 302 Moved Temporarily response pointing to a
dynamic endpoint at https://script.googleusercontent.com/macros/echo?..., where the response
is served via ContentService.
This redirection chain affects HTTP methods differently:
For GET requests, modern browsers follow the 302 redirect automatically when configured with
{ redirect: 'follow' }. The final response from script.googleusercontent.com returns with a
wildcard Access-Control-Allow-Origin: * header, allowing the browser to parse the JSON
response cleanly.
For POST requests, however, a preflight barrier emerges. When a client issues a POST request
with Content-Type: application/json, the browser sends an OPTIONS preflight request to verify
cross-origin permissions. The Apps Script gateway does not support OPTIONS requests,
causing the server to reject the call and the browser to block execution due to missing CORS
headers.
To bypass this issue, client applications must use simple requests. By formatting the POST body
as stringified JSON and setting Content-Type: text/plain, the browser skips the OPTIONS
preflight check. The Apps Script gateway accepts the request, triggers the 302 redirect, and
passes the payload to doPost(e). The server reads the raw string using
JSON.parse(e.postData.contents) and returns an OpenAI- or REST-compliant response via
ContentService.
// Server-Side Implementation (Code.gs)​

Tier
Google Sites acts as the administrative portal and front-end interface for the organization. It
integrates natively with Google Workspace Single Sign-On (SSO), automates SSL certificate
management, and maps page permissions directly to Google Groups. Because Google Sites
does not allow arbitrary server-side code execution or custom dynamic page routes, dynamic
interfaces are deployed using embedded Apps Script Web Apps (HtmlService) or custom
embedded HTML/JavaScript modules.

iframe sandbox. The legacy Caja and NATIVE sandboxes have been deprecated in favor of
standard HTML5 IFRAME mode. Embedded applications run inside an iframe hosted at a
unique subdomain under script.googleusercontent.com, which enforces several browser
security constraints:
The sandboxed frame cannot access the document object model, cookies, or local storage of
the parent page (e.g., Google Sites). External navigation must specify target="_blank" or use

Infrastructure as Code (IaC), Metadata as Code, and
CI/CD
To make deployments reliable and reproducible across regional offices or partner teams, all
configurations, folder structures, permissions, and application logic are managed as code.
The Google Command Line Apps Script Projects (clasp) CLI allows developers to manage
project files locally, compile TypeScript, run code analysis, and deploy scripts without using the
online Apps Script editor.
When deploying through continuous integration pipelines (such as GitHub Actions), clasp
requires an active OAuth 2.0 token. A developer runs an initial clasp login locally, generating an
authentication file at ~/.clasprc.json.
The refresh token from that file is stored as an encrypted secret in the CI/CD environment.
When code is pushed to the repository, the pipeline recreates the credentials and deploys

/**​
  * Calculates optimal supply route duration using native Maps service.​
  */​
function computeRouteMetrics(originAddress, destinationAddress) {​
   const directionFinder = Maps.newDirectionFinder()​
      .setOrigin(originAddress)​
      .setDestination(destinationAddress)​
      .setMode(Maps.DirectionFinder.Mode.DRIVING);​
​
   const directions = directionFinder.getDirections();​
   if (directions.status === "OK" && directions.routes.length > 0) {​
      const route = directions.routes[0].legs[0];​
      return {​
          distanceMeters: route.distance.value,​
          distanceText: route.distance.text,​
          durationSeconds: route.duration.value,​
          durationText: route.duration.text​
      };​
   }​
   throw new Error("Unable to calculate route directions.");​
}​

The system also uses multimodal capabilities to process receipts, paper surveys, and invoices
stored in Google Drive. Files are retrieved as binary blobs, base64-encoded, and submitted to
gemini-2.0-flash to extract line items, merchant details, and totals directly into Google Sheets

For semantic search across grant policies, project guidelines, and case files, the system
generates vector embeddings using gemini-embedding-001 or gemini-embedding-2-preview.
The resulting vector arrays (768 or 1536 dimensions) are stored alongside document IDs in an
indexing sheet. When a user runs a search, Apps Script converts the query into an embedding
and calculates cosine similarity across the stored vectors directly in the V8 runtime:
\text{Similarity}(A, B) = \frac{\sum_{i=1}^{n} A_i B_i}{\sqrt{\sum_{i=1}^{n} A_i^2}
\sqrt{\sum_{i=1}^{n} B_i^2}}
Because similarity checks run directly within the fast V8 runtime, searching thousands of vector
rows completes in milliseconds, providing semantic search capabilities without external vector
databases.

Architectural Synthesis
This architecture demonstrates that a complete NGO operations system can be hosted entirely
within the Google Workspace ecosystem without external GCP dependencies. By orchestrating
Google Sheets as an indexed relational datastore, Drive's content delivery nodes for
edge-cached static assets, Apps Script as an event-driven serverless compute runtime, and
Google AI Studio for cognitive automation, organizations can deploy an enterprise-ready
operations platform.
Bypassing external cloud infrastructure reduces hosting costs to zero beyond standard
Workspace licensing, simplifies disaster recovery, and ensures strong access control through
native Google identities.
Operating within platform quotas requires careful engineering—including LockService
concurrency controls, text/plain CORS preflight bypasses, self-scheduling trigger loops, and
cache optimization. With these patterns in place, the system delivers high availability,
sub-second query performance, and auditable governance, allowing non-profit organizations to
maximize their operational impact.
